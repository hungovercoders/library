- **Build record (AI in shot, attributable to the agent, not to dataGriff's feelings):**
  - Claude Code built the template in one session on 2026-11-14. The agent's sandbox would not run AWS Emulator, so every feature and fuzz run happened on GitHub Actions.
  - Two fresh agents implemented the example spec from the `implement-api` skill alone; CI was green on the first run both times.
  - A two-agent lifecycle test changed the spec of the implemented example and caught the implementation up, green first time. It exposed that the compatibility gate could not see a rule that changed while the contract's shape stayed the same; the gate now compares the feature files too.
  - The first `terraform apply` against the emulator in CI finished with "Apply complete! Resources: 15 added, 0 changed, 0 destroyed."
  - The current apply creates 23 resources (alarms and the authoriser were added after the first run). The run recorded in the post passed 50 scenarios, 278 steps and 411 generated fuzz cases.
  - After dataGriff asked how the features and the contract relate, a gate was added (`responses:check`, template issue #25) that fails when the contract documents a response no scenario received. Its first CI run found one in the example: `retire_beer 400`. The fix was a wider scenario, not code.
  - CORRECTION: the agent first said AWS Emulator 1.0.365 could not invoke a function, and built a local stand-in for API Gateway. dataGriff asked it to actually try ("Can you attempt to call the API from the emulator to see if that is true?"). A probe on GitHub Actions showed the emulator does invoke functions and serve HTTP APIs; the template's bundle failed to load only because of a createRequire line its own build added. dataGriff then chose "one truth": unit tests, and the full local stack. The stand-in was removed (template issue #26).
  - The emulated JWT authoriser checks a token's shape, issuer and audience, not its signature. IAM is not enforced as on AWS; the emulator's guide says not to test security on it.
  - Moving the tests onto the emulator's Lambda found one difference: a cancelled DynamoDB transaction reached the function without usable cancellation reasons, so a name clash returned 500 until the store told errors by name.
  - The run recorded in the post now: 23 resources, 53 scenarios, 290 steps, 396 generated fuzz cases; the `task ci` step took 2 minutes 21 seconds (56 seconds with the stand-in).
  - dataGriff on the speed of the full run, in their own words: "mention in the blog how quick the process is, the ci and testing I mean considering what it's doing, full environment, tests etc. mega confidence fast". Timings from the recorded run: scenarios 24.0 seconds, fuzz 47.25 seconds, the whole `task ci` step 2 minutes 21 seconds, including downloading and verifying the emulator.
  - dataGriff asked for a pre-push hook for fast feedback, with the skills turning on the right checks as the repository matures. `task check` runs the fast gates for the stage in `.stage` (template, spec, implemented); about 7 seconds warm on the implemented example (template issue #27).
